# Problem: Optimizing Architecture Context for LLM Agent Consumption

## Background

We run an AI pipeline that processes Jira issues (RFEs, strategies, bugs) through multiple analysis phases using Claude Code agents. Each agent invocation is a skill — completeness scoring, architecture mapping, fix generation, strategy review, security review, etc.

These agents need access to platform architecture documentation to do their work: verifying component existence, checking CRD definitions, validating port numbers, confirming dependencies, assessing feasibility of proposed changes. The architecture documentation covers ~70 components of an enterprise AI/ML platform (Red Hat OpenShift AI).

## Current Format

The architecture context is a directory of auto-generated markdown files:

```
architecture-context/
  architecture/
    rhoai-3.4-ea.2/           # version directory
      PLATFORM.md              # 870 lines — full platform overview + component inventory
      kserve.md                # 336 lines — one component
      odh-dashboard.md         # 415 lines
      vllm-cpu.md              # 288 lines
      ... (70+ component docs, ~300 lines each)
    overlays/
      0001-kfp-sdk-2.16.md    # patches/amendments to base docs
      ...
```

Total: ~74 markdown files, 26,000+ lines, 1.3MB. Each component doc is a comprehensive summary generated by an LLM from source code analysis, containing: metadata, purpose, architecture components table, CRD definitions, HTTP endpoints, configuration, dependencies, build details, and prose descriptions.

## Measured Agent Behavior (from 15,696 tool call spans across 2,000 traces)

Every agent that needs architecture context follows the same 6-step pattern:

```
1. Bash: ls .context/architecture-context/          → check existence
2. Bash: ls architecture/ | grep rhoai              → find version directory
3. Read: PLATFORM.md                                → read full 870-line inventory
4. Bash: ls rhoai-3.4-ea.2/ | grep -i <component>  → find relevant component docs
5. Read: 2-5 component docs (~300 lines each)       → read full docs
6. Bash: ls overlays/ ; Read overlays               → check amendments
```

### Quantified Problems

| Metric | Value |
|--------|-------|
| Total tool calls on architecture-context | 15,696 (8,327 reads + 7,369 bash) |
| Navigation overhead (ls, find, grep for filenames) | 54% of all tool calls |
| Traces that never successfully read a file | 20% (399/2,000) — all navigation, no content |
| Median files read per trace | 5 (PLATFORM.md + 4 component docs) |
| Lines read per trace (median) | ~2,100 lines (~30-40K tokens) |
| Useful lines extracted per component doc | ~50-60 out of ~300 (CRDs, ports, dependencies) |
| Architecture-context share of total pipeline input tokens | ~10-12% |

### What Agents Actually Extract

From a typical 300-line component doc, agents reference in their outputs:
- **CRD names and API groups** (one table, ~15 lines)
- **Ports and protocols** (one table, ~10 lines)
- **Dependencies** (a list, ~10 lines)
- **Purpose** (1-2 sentences, ~5 lines)
- **Key architectural decisions** (a few sentences)

The remaining ~250 lines (configuration details, build pipeline info, detailed prose, metadata) are read into the context window but rarely referenced in agent output.

### What Agents Search For

When running `ls | grep` to find component docs, the most common search terms are:
```
vllm, kueue, trusty, dashboard, model, notebook, eval, instruct, codeflare,
modelmesh, kserve, train, sdg, guardrails, llm, rhods, perses, automl
```

These are component name fragments. Agents are doing fuzzy filename matching because they don't have an index.

## The Core Problem

The architecture context is optimized for human reading (comprehensive markdown docs) but consumed exclusively by LLM agents. This mismatch causes:

1. **Navigation waste** — Agents spend 54% of their tool calls just discovering what files exist and where they are, before reading any content.

2. **Over-reading** — Agents read entire 300-line docs to extract ~50 lines of structured facts. The other 250 lines consume context window but don't contribute to the task.

3. **No queryable structure** — Cross-component questions (e.g., "does KServe support KEDA autoscaling?") require reading multiple full docs and inferring relationships. Dependencies and integrations exist implicitly in prose but aren't structured.

4. **Discovery failure** — 20% of traces fail to read any architecture content at all, typically due to directory structure confusion (broken symlinks, trying non-existent subdirectories).

## Constraints

- The generation pipeline that produces these docs is separate and shouldn't change. It scans source repos and outputs comprehensive markdown — that's its job.
- Agents run as Claude Code sessions with access to: Read, Bash, Grep, Glob, Write, Edit tools. No vector database or embedding search available.
- The architecture context is vendored into the working directory (git clone, possibly sparse). Agents access it via filesystem tools.
- Multiple skill types consume the context (strategy review, feasibility assessment, bug mapping, security review), each needing different subsets of information.
- The solution needs to work within the existing tool call model — agents read files, they can't query APIs.

## What We're Looking For

An intermediate representation or index format that sits between the comprehensive generated markdown and the agents that consume it. Something that:

1. Eliminates the navigation loop (agents should know what exists and where without `ls | grep`)
2. Provides structured facts (CRDs, ports, dependencies, API groups) without reading full docs
3. Supports cross-component queries (dependency graphs, integration points)
4. Preserves access to full prose docs for deep-dive questions
5. Works with filesystem-based tool access (Read, Bash, Grep)
